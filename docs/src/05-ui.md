# UI: layouts, handlers, drawing

The game's UI is built from **layout files** (`.ui`, SNO group UI). A layout is a tree of controls. Each control has a **type**, numeric **properties** (position, size, flags) and **styles** (strings: handler names, texture names, text keys, template references). A mod can change stock layouts, add new ones (`data/Base/UI/*.ui`) and drive them from client code.

## Control paths

A built layout lives under a layer: `Root.NormalLayer.<LayoutName>_main.LayoutRoot....`. For example:

```
Root.NormalLayer.BattleNetCampaign_main.LayoutRoot.Menu.PlayGameButton
Root.NormalLayer.BattleNetAuctionHouse_main.LayoutRoot.OverlayContainer.PageHeader...
```

- `find(fullPath)` gets a registered control.
- `child(control, ".A.B")` gets anything below it. Rows of list boxes and template instances are only reachable this way.

## Finding controls

- `D3ModTool ui-info <file.ui>` lists a layout's controls, with types and how many styles and properties each has.
- `D3ModTool ui-info <file.ui> --full` also prints every property and style.
- `dump_controls("text")` logs the registered controls of the running game whose path contains the text, for example `dump_controls("BattleNetCampaign_main")`.
- `report_missing(path)` (Rust) logs the deepest part of a path that exists, which helps when a path is wrong.

Extract stock layouts with `D3ModTool casc-extract UI <nameRegex> <outDir>`.

## Control types

| Type | Kind |
|---|---|
| 13 | list box: rows come from a template, see below |
| 17 | draw-hook control: its style 44 names a draw function |
| 20 | dropdown (UIComboBox) |

Buttons, labels, text boxes and windows use other types. `ui-info` shows each control's type, and `ui-type` changes it.

## Properties

These are integers, set with `D3ModTool ui-prop <file> <control> <id> <value>`.

| Id | Meaning |
|---|---|
| `0x07`, `0x08` | x, y (relative to the parent; UI units) |
| `0x09`, `0x0A` | width, height |
| `0x3D` | text horizontal alignment: 2 center, 3 right |
| `0x87` | dropdown: visible rows |
| `0x97` | starts hidden (1); show it from code |

## Styles

These are strings, set with `D3ModTool ui-style <file> <control> <id> <string>` and removed with `ui-style-remove`.

| Id | Meaning |
|---|---|
| 41 | click handler name |
| 44 | draw hook name (type-17 controls); must be one of the 9 stock names |
| 99 | per-frame update handler |
| 101 | selection changed (list boxes, dropdowns) |
| 105 | tooltip handler (called every frame while hovered) |
| 158 | template reference |
| 187 | list box row template |
| 1 with value `"1"` | marks a control as a template (not built by itself) |

## Handlers

A layout names a handler with a string style. When the screen is built, the game looks the name up:

- **Names the exe has** run the game's code. Wrap them with `register_wrapper` to run before or after it, or instead of it.
- **Names the exe lacks** resolve through the host to a `register_handler` function. That is how your own layout gets behaviour: invent a name such as `MyMod_OnClick_Buy`, put it in style 41, and register it.

Click handlers can be called for several mouse events of one click, so make them idempotent. For example, "open" should do nothing if the window is already open.

## List boxes

A list box (type 13) has a row template (style 187). From code:

```rust
let i = api::list_add(list);                 // a new row, from the template
let row = api::list_get(list, i);
api::set_text(api::child(row, ".ItemName"), "Ring of Royal Grandeur");
```

Rows can't be removed. Keep your own count of rows created, reuse them, and hide the ones you don't need. `D3ModTool ui-make-listbox` turns a static row of a layout into a list box with that row as its template.

## Drawing

2.8 resolves draw-hook names (style 44) only from a fixed table of 9 stock names:

```
UIShop_Draw, UIInventory_Draw, UIInspect_Draw, UIEquipmentManager_DrawInventory, PlayerInspect_InventoryDraw,
UITransmute_DrawGrid, UIHireling_Draw, UIGameBase_Draw, UIStash_Draw
```

To draw inside your layout:

1. Give your type-17 control the style 44 name of a stock window that is **not shown at the same time** as yours. At the main menu, for example, the follower window never draws, so `UIHireling_Draw` is free there. Avoid `UIGameBase_Draw`.
2. Wrap that name with `register_draw`. In the wrapper, draw only while your screen is shown; otherwise call `original`.
3. Draw with `draw_texture`, `draw_item_icon` and `control_rect`, all in UI units.

**Depth:** draw calls take the frame's `depth` counter. Each draw goes to `z = 0.9999 - depth × 1e-4` and increases the counter. To draw *over* a later sibling, such as an icon over a dialog frame, advance the counter yourself before drawing.

Useful stock textures:

- `UI:Stash_Slot_Empty`, `UI:InventoryGrid_Slot`
- the quality backgrounds `UI:Quality_{Large|Small}_{Inventory|Equip}_{Magic|Rare|Set|Legendary}`, with an optional suffix `_Primal`, `_Primalized`, `_Sanctified` or `_SeasonOnly`
- `UI:Tab_Stash01_Selected` … `UI:Tab_Stash53_Unselected`
- `UI:SlotFlash_Generic`

## Tooltips

Give the hovered control a style 105 handler. In it, call `show_item_tooltip(rcx, generator, ...)` every frame while hovered. The tooltip is the game's own, with stats, sockets, set bonuses, ancient and primal frames, so your server part only has to send the item's `D3.Items.Generator` bytes.

## Dropdowns

A type 20 control. Fill it with `combo_set_items`, read it with `combo_selected`, and react to changes with a style 101 handler. Note that the style 101 handler's `rcx` points at the combo's handle field, not at the combo itself.

## Screens are rebuilt

Joining or leaving a game tears down the UI screens. A layout you built with `create_layout` is gone afterwards. Before showing it, check `find("Root.NormalLayer.<Name>_main")`. If it is null, build it again and reset everything that pointed into the old copy: list row counts, selections, dialogs.
